# Security model

This lists every promise Vault makes about security and privacy: where it's made, the code that keeps it, and the
test that pins it. [`MANIFESTO.md`](../MANIFESTO.md) sets the principles; this file says what's built.

A change that adds, changes or breaks a promise updates this file in the same pull request. IDs never change or get
reused: a new promise takes the next free number, in the area it belongs to.

To report a security problem, see [`SECURITY.md`](../SECURITY.md).

## How to read it

- **Promise** is what Vault does, in plain words.
- **Made in** is where users or contributors are told it: the README, the manifesto (C1–C10), the in-app help
  (FAQ pages), the changelog, the item editor or a settings screen, and
  [`docs/on-device-encryption.md`](./on-device-encryption.md) (the design doc). "This file" means only this file
  says it.
- **Kept by** names the types that keep it, under `Vault/Sources`. Search for them by name.
- **Pinned by** names the test suite and test, under `Vault/Tests`, or under `VaultApp/VaultAppUITests` and
  `VaultApp/VaultMacAppUITests` for UI tests, or `VaultApp/VaultMacAppTests` for tests inside the running Mac app, or
  "none". A promise kept only by something being absent, like analytics, has no test.
- **Status** is "Holds", or "Holds, with a limit" and the limit. The bigger limits are gathered in
  [Accepted limits](#accepted-limits).

## Who it protects against

- **Someone forcing you to unlock Vault**, at a border, in a robbery or at home. This is the manifesto's core case.
  Face ID and the passcode don't stop them. The App Lock Password, a duress password, killphrases and hidden items
  are for them.
- **Someone who picks up your unlocked iPhone, or sits down at your unlocked Mac.** App Lock and locked items are for
  them.
- **Someone with a copy of Vault's files**, from a lost iPhone or Mac, or one of their backups. The App Lock Password
  encrypts the vault for them, and every backup Vault makes is encrypted. On the Mac, the password is always on.
- **Other apps and other devices**, through the clipboard, the keyboard, widgets, QuickType, Spotlight, AutoFill, and
  on the Mac, screen capture and the windows other apps can see.

It doesn't protect against a jailbroken or otherwise compromised iPhone or Mac, someone with an administrator's
access to the Mac, iOS or macOS themselves, someone watching the screen, or a password that can be guessed.

## The Mac app

The Mac app (`docs/mac-app.md`) keeps every promise above that its shared code keeps, which is most of them: duress,
the vault file, the cryptography, backups and transfer, and offline and supply chain hold unchanged, through the same
code. The rows below are its own.

Some rows above have a Mac version here:

- G22, G29: the Mac locks when another app comes to the front rather than in the background, and at once when the
  screen locks or the Mac sleeps (G86).
- G24: windows are kept out of every capture, rather than covered once capture is noticed (G91).
- G25, G31: Touch ID, an Apple Watch or the Mac's login password, rather than Face ID or the passcode (G85, G88, G93,
  G95).
- G41: a recovery phrase's words also hide while Vault isn't the active app (G88).
- G44, G45: widgets show Vault locked whenever it's locked, rather than whenever the password is on, and show the
  codes the unlocked app hands them otherwise, never a locked or hidden one. There's no Lock Screen or StandBy, and
  copying from a widget asks for the Mac to be unlocked (G98).
- G46: the identity store is always empty, as the password is always on (G95).
- G50, G51, G52: the Mac's clipboard, fields and keyboard (G87, G89).
- G18, G22: erasing after failed passwords and the Require Unlock delay are kept in the keychain, not the App Group's
  defaults (G96).

Some don't apply on the Mac:

## Accepted limits

These are known and accepted. Each is said where users will read it.

- **Without an App Lock Password, the vault isn't encrypted by Vault.** It's a SQLite store that iOS Data
  Protection covers only while the iPhone is locked. Anyone who can read it sees every item, and which items are
  hidden or have a killphrase. It's in the iPhone's own backups to iCloud or a computer, as other apps' data is, and
  without Advanced Data Protection Apple can read an iCloud Backup. Setting an App Lock Password encrypts the vault
  on the iPhone and in those backups. (G38)
- **Killphrases match as you type.** Every change to the search is checked against the whole search, capitals
  counting and spaces at either end ignored. So a killphrase fires on the way to typing a longer search that starts
  with it. Only Vault's own search checks killphrases, not AutoFill's. (G1, G2)
- **Backups carry the keys that check phrases.** That's what keeps killphrases and search passphrases working once
  a backup is restored. It also means anyone who can decrypt a backup can test guesses at its phrases, so a phrase
  shouldn't be a password used anywhere else. (G7, G56)
- **Backups with the same password share a salt.** A backup's key derivation salt is chosen when its backup password
  is set, and stays the same until the password changes. So, without decrypting anything, backups made with one
  password can be told apart from those made with another. (G55)
- **Items and backup passwords from before v2 keep their lighter key derivation until they're used.** An item
  encrypted before v2 moves to v2's Argon2id only when its password next opens it, and a backup password set before
  v2 only when a Backups page next loads it. Until then, and in every copy made before, such as an earlier backup, an
  iPhone backup or a backup PDF, a guess at the password costs only v1's derivation: for an item, scrypt and PBKDF2,
  much less than the App Lock Password's Argon2id. A backup password carried on to v2 keeps its salt, so an older
  backup made with it can be attacked at v1's cost, and what that finds opens the newer backups too. Give encrypted
  items long passwords, such as a few random words, and open them once after updating. (G42, G55, G68)
- **Backup and item passwords need a lot of memory to derive.** v2's Argon2id takes 512 MiB for a backup and 256 MiB
  for an item, so it only ever runs in the app. On an iPhone short of free memory, iOS could end the app part way
  through a restore, or while it moves a backup key on, which then stays as it was. Nothing is lost, and trying again
  with fewer apps open works. (G55, G68)
- **On iOS, the widget extension can read the device key.** While the App Lock Password is off, the widgets show
  codes from the vault, as they do when there's never been a password, and the device key is what opens it then. So
  it stays in the App Group's keychain access group, which the widget extension has. The count of wrong passwords and
  the wrap stamp are kept where only Vault and its AutoFill extension can read them. With the password on, there's no
  device key. (G28, G44, G99)
- **Some build tools are prebuilt binaries.** mockolo, SwiftFormat and SwiftLint are downloaded as binaries pinned
  by checksum. They run only while building. mockolo writes the mocks that are compiled into the package's modules.
  (G74)
- **Duress vaults nest safely eleven deep.** A duress vault can have its own, and so on. For eleven levels, none can
  touch the real vault. Beyond that, each new duress vault has up to a one in five chance of taking the real vault's
  place. (G13)
- **A duress password starts the waits again.** Any vault's password resets the count of wrong passwords, so
  someone who knows a duress password can make four wrong guesses at another vault's password, open the duress
  vault, and do it again, as often as they like. Neither the waits nor erasing after 10 slow them down on the
  iPhone, only the key derivation, about a second a guess (half a second on a vault file made before VAULT-128). A
  long App Lock Password is what keeps the real vault safe. (G19)
- **On the Mac, something running as you, with your consent, can copy the vault file.** macOS keeps other apps out
  of Vault's App Group unless you allow them, or give them Full Disk Access. Anything you do can copy the vault file
  and try passwords on it elsewhere, as with a copy of an iPhone's files: a long App Lock Password is what protects
  it. It could also change the settings kept beside the vault that anyone at the unlocked Vault can change, such as
  Hide While Recording, but not erasing after failed passwords or the Require Unlock delay, which are in the
  keychain (G96). (G85, G94)
- **On the Mac, Time Machine's local snapshots keep earlier copies of the vault.** They're of the whole disk, so they
  hold the vault file as it was, and so do Time Machine's backups made before Vault kept the vault out of them, or
  while Keep Out of Time Machine was off. An item a killphrase deleted, or a vault Delete All Data or an erase removed,
  can come back from one with the App Lock Password it had then. (G6, G15, G18, G63, G97)
- **A vault that hasn't opened since vaults kept their own keyrings still needs the keychain.** Before, every vault
  on a device checked its phrases with the same keys, in the keychain. An encrypted vault takes its copy the first
  time it opens, and a vault can't tell whether there are others, so the keychain keeps them. A vault moved to another
  Mac, or restored onto another iPhone, before it has opened once loses them, and so does a duress vault that hasn't
  been opened. Open each vault once before moving it, or move with a Vault backup, which carries them. Every vault that
  took a copy also has those keys to match against, so a backup of a duress vault made then carries the keys the real
  vault's phrases from then were digested with, as it always did. (G7, G100)
- **Without an App Lock Password, killphrases and search passphrases don't move with the vault.** Their keys stay
  in the keychain, never beside the digests in a store that isn't encrypted, and so do a vault's while the password
  is off. Move with a Vault backup, which carries them. (G7)
- **On the Mac, other apps using the camera see what Vault scans.** Vault won't scan while another app is using the
  camera, but one that starts using it meanwhile sees the code too. Choose an image instead. (G90)
- **On the Mac, windows macOS draws for Vault aren't kept out of captures.** The Open panel's preview, an input
  method's candidate window, Hover Text and Zoom, the Touch ID prompt and Control Center's camera preview are
  macOS's, not Vault's. (G91)
- **On the Mac, the print panel can send a backup on.** Its PDF menu opens the backup in Preview, or sends it in
  Mail or Messages, as it does for anything printed. Only Print and Save as PDF count as a backup. (G93)
- **On the Mac, apps you've allowed to control it can read Vault.** An app with Accessibility access, in Privacy &
  Security, can read what Vault's windows show, and what's typed into its fields, while they show it, as a screen
  reader must. Secure Keyboard Entry only keeps keystrokes from apps watching the keyboard. (G89, G92)
- **On the Mac, a widget can show codes for a few minutes after Vault locks.** Vault takes its widgets' codes back
  the moment it locks and asks macOS to reload them, but if macOS holds the reload back, or Vault stops without
  locking, as when it crashes, or the codes can be neither deleted nor replaced as the Mac locks and it's unlocked
  again before they can, a widget goes on showing the codes it was given until they run out: five minutes at most,
  and never a stale code. Widgets are drawn by macOS, so Hide While Recording doesn't keep them out of captures.
  A widget's settings keep the site and account of the code it was set up with until it's removed, and with a duress
  vault open, a widget set up for another vault's code shows it unavailable, as for a code that's been deleted. Don't
  put a code you'd hide from someone forcing you to unlock Vault on a widget. (G98)
- **On the Mac, hiding windows from capture depends on macOS.** Vault asks macOS to leave its windows out of every
  capture, and it's checked by hand on each version of macOS (`RELEASE.md`), but Vault can't make it do so. That's
  most uncertain for the AutoFill sheet, which macOS shows inside the app it fills. (G91, G95)
